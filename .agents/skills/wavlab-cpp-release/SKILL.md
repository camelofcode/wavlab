# Release WavLab C++

Use this skill when preparing, tagging, publishing, or auditing a C++ release.
Publishing tags and GitHub Releases changes external state: do it only when the
user has explicitly requested publication.

## Release invariants

- Use semantic versions and tags of the form `vX.Y.Z`.
- `project(VERSION ...)`, CLI `--version`, package config version, tests, the
  changelog heading, tag, and GitHub Release must agree.
- Tags are immutable release records. Never move, replace, or delete a
  published release tag without explicit user direction.
- Release only a commit on protected `main` whose `Required C++ checks` passed.
- Do not publish directly from an unmerged preparation branch.

## Prepare the release

1. Confirm `main` is clean and synchronized; inspect existing tags/releases so
   the version is unused.
2. Create a focused `release/vX.Y.Z` branch.
3. Update `project(VERSION ...)` and any test that asserts the exact CLI
   version.
4. Keep an empty `Unreleased` section at the top of `CHANGELOG.md`; move the
   accumulated entries into `## [X.Y.Z] - YYYY-MM-DD`.
5. Regenerate CLI documentation only if parser definitions changed.
6. Run the ordinary development gate from `wavlab-cpp-development`. Also run
   the Release preset when release-specific CMake/install logic changed.
7. Commit, push, open a PR, and wait for `Required C++ checks`. Merge through
   the protected branch.

## Publish

1. Synchronize local `main` and verify the merge commit's required workflow is
   successful.
2. Recheck that the tag and GitHub Release do not already exist.
3. Create an annotated tag on the exact `main` commit:

   `git tag -a vX.Y.Z -m "WavLab vX.Y.Z"`

4. Push that exact tag, then create the GitHub Release from it. Use the
   matching changelog section as release notes; do not use an unrelated commit
   summary.
5. Verify with `git ls-remote --tags`, `gh release view`, and a clean checkout
   or archive inspection. Confirm the built CLI reports `X.Y.Z`.
6. Report the tagged commit and release URL. Do not silently publish packages
   or binary assets; source archives generated by GitHub are sufficient unless
   the user requests an artefact workflow.
